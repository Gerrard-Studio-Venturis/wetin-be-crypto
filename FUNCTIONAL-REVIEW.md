## Concrete PD-07 choices — all proposed, not approved

The following preferred package makes the open contracts reviewable. Numerical duration and checkpoint choices are planning hypotheses, not measured audience preferences. They preserve the approved 30 days after the last qualifying learning activity; they do not replace it with a fixed 30 days after first arrival or consent.

### PD-07-V — Define a current visit without device memory

Propose a **two-hour idle visit**, beginning with a deliberate learning interaction and ending after two hours without deliberate learning interaction or an explicit End this visit action. Lesson/glossary navigation and genuine learning-state actions keep the visit active; article browsing, search, sign-in and background polling do not. Normal learning navigation/reloads within the active visit preserve available state. A shorter 30-minute idle cap is an alternative with faster shared-device expiry but more interrupted study; no learner evidence presently selects either.

Use server time and a nonpersistent guest capability for the proposed no-memory mode; the technical mechanism remains unproven. Browser close is not a guaranteed end because a browser may restore its session. If it restores the key within the approved idle boundary, this is still the same defined visit; after the boundary the server rejects old eligibility. Do not claim that closing a tab reliably clears work. If the key is lost, a new visit cannot recover private guest records merely by claiming an identity.

Proposed explanation: “Progress is kept during this visit. The visit ends after two hours without learning activity, or when you end it. Device memory or an account lets you return later.” Review this wording with learners before adoption. Duration, supported storage fallback and explicit-end behaviour need owner approval.

### PD-07-C — Let genuine changed-state checkpoints count

Prefer explicit lesson completion, an accepted check/mission submission, and a **meaningful changed-state checkpoint**: a deliberate answer-change/Next action saved for an unfinished activity, or an explicit Save my place reading-position action. Server acknowledgement must identify a valid content/activity version and changed recorded work. A first valid recorded checkpoint can establish the learning timestamp; a duplicate/replayed acknowledgement or unchanged background save does not advance it. These are proposed functional actions, not existing controls or learning credit.

The simpler alternative is completion/submission only. It needs fewer checkpoint rules but unfinished reading/practice does not extend remembered progress. With the preferred choice, a checkpoint can preserve unfinished work and refresh retention without completing a lesson, passing a check, demonstrating practice or making retired evidence current.

For opt-in memory, propose a rolling guest-container deadline **30 consecutive 24-hour periods after the last server-accepted qualifying learning event**. Eligible records share that deadline; activity applicability is checked separately. Enabling memory can retain valid current-visit records, using their last qualifying event rather than inventing learning from the consent click. Record the opt-in separately. Article reading, bookmarks, search, My Journey viewing, authentication, background requests and idempotent retries/imports cannot refresh this deadline.

Expiry is checked before accepting new guest writes. An expired container cannot be renewed to resurrect old passes; a new authorised guest context may start fresh work. A later checkpoint changes no assessment's retired status. Precise event definitions, acknowledgement/recovery and opt-in-with-no-recorded-work behaviour remain PD-07 conditions.

### PD-07-I — Confirm per record, then clean only confirmed copies

Prefer a recoverable **per-record import**, using an explicit progress-save/add intent and one authenticated target account. Validate source authority, unexpired guest scope, record identity/version and permission when committing each new account record. Propose no import grace window: a request started before expiry does not permit an uncommitted record to be copied after its server deadline or clearing. Confirm each account result before treating that item as saved. Repeating requests or resuming an interrupted operation reconcile already-confirmed items rather than add duplicates. A true later assessment attempt remains distinct.

Confirmation means a durable server-side account write or verified existing record, not merely sending a request or receiving a provisional response. If acknowledgement is lost, recovery first checks the operation under its original authorised account: an already-committed record stays confirmed even if the guest has since expired; an uncommitted item must still satisfy source eligibility at its new durable write. Record eligibility for importing valid history differs from applicability for a current gate: a recognised, unexpired older-version attempt may be retained as history without granting current credit. Original responses/results are not silently regraded.

Propose the following cleanup choices:

| Situation | Preferred proposed behaviour |
| --- | --- |
| Entire valid import confirmed | Remove the confirmed migrated copies from active guest records; revoke/rotate the old guest capability as required. Confirm account saving and the return destination. |
| Only some items confirmed | Remove only confirmed migrated copies. Keep genuinely recoverable unresolved guest work to its existing expiry; no retention extension from import. Show item-level summary and retry. |
| An item already exists in the account | Confirm its reconciliation by stable identity/version; no extra completion count or duplicate attempt. Treat the reconciled guest copy as confirmed for cleanup. |
| Guest source expires or is cleared before an uncommitted item's durable write | Recover prior durable account writes by operation identity even if the browser missed their acknowledgement; do not import the now-ineligible uncommitted remainder. Explain the result and relevant fresh-work route. Expiry is not a reason to erase account history. |
| Import declined, authentication fails, or Save article is the intent | No silent learning import or import cleanup. Preserve available guest work under its existing rules. Bookmark confirmation remains independent. |
| Account changes during recovery | Stop displaying/updating the previous account's private operation through the new account. Require the correct account and its explicit intent; do not retarget pending writes automatically. |

Keeping all guest copies after success is an alternative, but leaves more shared-device history and repeated-import handling. Clearing every guest record after partial success would discard recoverable work and is not recommended. Key rotation/rebinding must preserve permitted unresolved work and stable provenance; the detailed mechanism needs a delivery specification and later tests.

Example: account A/B plus guest B/C and a weaker attempt produces three unique completions with the original pass retained. If B is reconciled and C confirms but the attempt write fails, only the confirmed guest copies are cleaned; the attempt remains unresolved until a valid retry or ordinary expiry. Never label the whole operation saved while an item is unresolved. Assume the example's applicable identities/versions match; real version changes need the declared applicability rules.
